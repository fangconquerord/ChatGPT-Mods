# Performance: long streamed responses can trigger expensive DOM/React scans and layout work

## Summary

Long ChatGPT responses, especially responses containing code blocks and the action toolbar added at the end of generation, can cause noticeable UI stalls with the extension enabled.

I audited the current upstream `main` source and found several hot paths that are executed from document-wide `MutationObserver`s. The most important ones are in `content-message-meta.js` and `content-chat-exporter.js`.

This is a source-level performance report and refactor proposal. I am **not** claiming a measured speedup for upstream yet; the suggested changes should be validated with a Chrome Performance trace / long-chat stress test.

## 1. `content-message-meta.js`: timestamp extraction traverses React internals

The timestamp feature is bundled into the `fileInfo` runtime. The code reads private React fields (`__reactProps$...` / `__reactFiber$...`) and recursively walks the resulting object graph through `findTimestampInObject()`.

Relevant pattern:

```js
function getReactProps(el) {
  for (const key in el) {
    if (key.startsWith("__reactProps$") || key.startsWith("__reactFiber$")) {
      const value = el[key];
      if (key.startsWith("__reactFiber$") && value?.memoizedProps) {
        return value.memoizedProps;
      }
      if (value) return value;
    }
  }
}

function findTimestampInObject(obj, depth = 0, seen = new WeakSet()) {
  // ...
  for (const [key, value] of Object.entries(obj)) {
    // ...
    const nested = findTimestampInObject(value, depth + 1, seen);
    // ...
  }
}
```

The message timestamp path also scans message DOM descendants and is scheduled from a document-level mutation observer. On a large rendered response, this can turn a UI metadata feature into work proportional to message complexity.

### Proposed change

Do not inspect React private fields for timestamps during normal rendering.

Prefer one of these approaches:

1. Fetch `/backend-api/conversation/<conversation-id>` only when the browser is idle, map timestamps along the current `current_node -> parent` branch, then write timestamps once; or
2. Move timestamps into a separate optional feature and update only newly finalized messages.

Important constraints:

- no React Fiber/private-props traversal;
- no `querySelectorAll("*")` on message bodies;
- no processing on every streamed DOM batch;
- process an already timestamped message at most once.

## 2. `content-chat-exporter.js`: `.innerText` and snippet injection are on the streaming hot path

`getVisibleText()` currently starts with:

```js
function getVisibleText(node) {
  return String(node?.innerText || node?.textContent || "")
    // ...
}
```

`innerText` can require style/layout information. When called immediately after DOM mutations, the browser may need to synchronously update style/layout before returning the result.

The exporter also continuously discovers code blocks and copy/action buttons so that it can inject per-message/per-code-block export controls. DOM changes generated by streaming Markdown, code blocks, and the final message action toolbar can therefore wake exporter work even when the user is not exporting anything.

### Proposed change

Make chat export **lazy / user-triggered**:

- keep one top-level `Save / Export` control;
- remove the document-wide observer used only to inject snippet buttons;
- do not read full message text in the background;
- scan/clone the conversation only after the user clicks Export;
- prefer `textContent` on cloned/sanitized DOM when visible-layout semantics are not required.

This moves export cost from every response render to the actual export action.

If per-message export buttons are considered important, a safer alternative is to attach them only after an explicit hover/context-menu action, or process a finalized turn once rather than reacting to all streamed mutations.

## 3. `content-split-view.js`: observer is active even before split view is opened

The split-view feature installs a document-wide observer even while split view is inactive, and the split-frame patching path also observes iframe DOM/attributes.

### Proposed change

Before split view is opened, use lifecycle events only (`pageshow`, `popstate`, `hashchange`, `resize`) to maintain the top-level button.

Create iframe-specific observers only after the user opens split view, and disconnect them when it closes.

## 4. Multiple independent document-wide observers

Several content scripts independently observe `document.documentElement` with `subtree: true`. Even when individual callbacks are small, every streaming mutation batch is delivered to each observer, so costs accumulate.

A useful architectural target would be:

> During a normal ChatGPT streamed response, extension code should do no work proportional to the assistant message body unless that feature explicitly needs streaming updates.

Sidebars should observe the sidebar root, composer features should observe/follow the composer, and export should be lazy.

## 5. `manifest.json`: `all_frames: true`

The current manifest loads the content-script bundle with:

```json
"all_frames": true
```

Some individual scripts immediately return outside the top frame, but the bundle is still injected into matching frames and not every module has the same top-frame guard. This is unnecessary overhead for features that are top-page UI enhancements.

### Proposed change

Use `all_frames: false` for the main content-script bundle. If a specific split-view feature later needs frame-side code, load only that minimal frame-specific script explicitly.

## Suggested implementation order

1. Refactor `content-chat-exporter.js` to user-triggered export; remove background snippet injection / global observer.
2. Refactor timestamp extraction in `content-message-meta.js`; remove React-private-object traversal from the render path.
3. Make split-view observation active only while split view is open.
4. Scope temp-chat / prompt-enhancer / organizer observers to their actual UI roots or lifecycle events.
5. Change the main manifest bundle to `all_frames: false`.
6. Add a regression benchmark / browser test that simulates a long conversation and repeatedly appends streamed DOM nodes.

Suggested regression metrics:

- observer callback count during one long streamed turn;
- number of full-document `querySelectorAll` calls;
- number of layout-sensitive reads (`innerText`, `getBoundingClientRect`, `getComputedStyle`) during streaming;
- main-thread long tasks before and immediately after final action-toolbar mount.

## Expected behavior

With export/file-info/split-view enabled but unused, generating a long response should have approximately constant extension overhead relative to message length, and finishing a response should not produce a large synchronous extension task simply because the message body is large.
